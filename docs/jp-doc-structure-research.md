# 日本語ドキュメント生成ハーネス向け「文書構成の選択ルール」調査と Microsoft APM 形式スキル設計

構成を決める最大の要因は「読者がこの文書を読み終えて何をするか（読者の目的）」です。これで構成の系統が決まり、「読む姿勢と時間」が結論の位置を、「専門性」が深さと前置きの量を決めます。スキルはこの3段階の判断と、ジャンル別の骨子カタログで組み立てるのが妥当です。「Microsoft APM 形式」は、microsoft 組織が MIT ライセンスで公開している Agent Package Manager（APM）だと確認できました。スキルは `apm.yml`（必須は `name` と `version`）と `.apm/skills/<name>/SKILL.md`（Agent Skills 標準の frontmatter）で作ります。

## TL;DR

- **構成選択のルール**：(1) 組織の定型があればそれを最優先する。(2) 読者の目的（決める／報告を受ける／作業する／学ぶ／調べる／理解する／動かされる／検証する）で構成の系統を選ぶ。(3) 読む姿勢で結論の位置を決める。(4) 専門性で前置きと深さを調整する。文化審議会「公用文作成の考え方」（2022年）も木下是雄『理科系の作文技術』も「結論・重点を先に」を基本としているため、既定は結論ファーストとし、積み上げ型はチュートリアル・教材・論文本文などに限る。
- **ジャンル別の骨子**：一次情報で骨子を確認できたのは、Diátaxis（4象限）、IMRaD、ピラミッド原則と SCQA、Google のデザインドキュメント、Google SRE のポストモーテム、Nygard 形式の ADR、Amazon の PR/FAQ、IPA の要件分類、公用文の標題・見出し・文体の規則。稟議書・PREP・SDS などの日本のビジネス慣習は、実務解説サイトに共通する構成に基づいて整理した（単一の原典はない）。
- **APM 形式**：スキルは `.apm/skills/jp-doc-structure/SKILL.md` に置く。`name` は小文字・数字・ハイフンのみで64字以内、ディレクトリ名と一致させる。`description` は1024字以内で「いつ使うか」から書き始める。本文は500行・5000トークン以内に収め、詳細は `references/` に分けて「LOAD references/…」で読み込ませる。`apm install` で Claude 向けには `.claude/skills/`、Copilot・Cursor・Codex・Gemini 向けには `.agents/skills/` に配置される。

## 1. 調査結果の要約（構成選択の原理原則）

- **原理1（目的が構成を決める）**：同じ内容でも、読者の目的が違えば構成は変わる。Diátaxis は「行動（action）か認識（cognition）か」「技能の習得（study）か応用（work）か」の2軸で、チュートリアル（行動×習得）、ハウツー（行動×応用）、リファレンス（認識×応用）、解説（認識×習得）の4種類に分ける。ビジネス文書向けに「決める」「報告を受ける」「動かされる」を加えると、ほぼ全ジャンルを網羅できる。1文書には1つの主目的（木下の言う「一文書一主題」）を持たせる。
- **原理2（重要なものを先に）**：文化審議会の「公用文作成の考え方」（令和4年1月7日建議、同1月11日に内閣官房長官から各府省へ周知通知）は、文書の構成について「文書の性格に応じて構成を工夫する」「結論は早めに示し、続けて理由や詳細を説明する」「通知等は既存の形式による」「解説・広報等では読み手の視点で構成を考える」「分量の限度を決めておく」を挙げている。木下是雄『理科系の作文技術』（1981年）の「重点先行主義」も、ピラミッド原則や BLUF も同じ立場である。起承転結（「転」で話題を転じる構成）は仕事の文書の型にしない。積み上げ型が正当化されるのは、学習順序に意味がある場合（チュートリアル、教材）と、検証の手順を追わせる場合（論文本文）に限られる。
- **原理3（読者の期待する位置に置く）**：定型のあるジャンルでは定型そのものが品質基準になる。Sollaci & Pereira（2004, *Journal of the Medical Library Association* 92(3):364–367）によれば、IMRaD は調査対象誌で1940年代に使われ始め、過半数に採用されたのは1970年代になってからで、読者が決まった位置の情報を拾い読みする「モジュール読み」を容易にする（"The IMRAD structure facilitates modular reading"）。
- **原理4（意思決定文書には非目標と代替案）**：Google のデザインドキュメントは「メタ情報 → 背景・スコープ・目標 → 概要 → 詳細設計 → 横断的関心事 → 代替案」の順で書く。非目標は、industrialempathy.com の記事「Design Docs at Google」で「『システムがクラッシュしない』のような目標の否定ではなく、目標にもなり得たが、あえて目標にしないもの」と定義されている。
- **原理5（見出しだけで筋が通る）**：公用文の考え方は、見出しを追えば全体の内容がつかめること、標題と見出しを呼応させることを求めている。Google の technical writing コースも、アウトラインの各ステップを1つの概念か1つのタスクに限るよう勧めている。
- **原理6（範囲の宣言と段階的開示）**：Google Technical Writing Two は、冒頭で「何を扱うか・読者に期待する前提知識・何を扱わないか」を示し、長い文書では新しい情報を必要になった時点で出す（Disclose information progressively）よう説いている。

## 2. 構成選択ルール

### 2.1 判断軸の定義（支配度の高い順）

| 順位 | 判断軸 | 取り得る値 | 構成への効き方 |
|---|---|---|---|
| 0 | 定型の有無 | 組織・業界・法令の書式あり／なし | ありならそれを骨格として採用し、以下の軸は中身の調整にだけ使う |
| 1 | 読者の目的 | 決める（承認）／報告を受ける／作業する／学ぶ／調べる／理解する／動かされる（依頼・説得）／検証する（学術） | 構成の系統（ジャンル）を決める |
| 2 | 読む姿勢・時間 | 通読／拾い読み・検索／冒頭だけ（多忙な意思決定者） | 結論の位置、要約の要否、見出しの粒度を決める |
| 3 | メッセージ種別 | 主張・提言／意思決定の記録／事実の報告／手順の指示／概念の説明／比較評価／教育 | 同じ系統の中での型を決める（PREP か SDS か、ADR かデザインドキュメントか） |
| 4 | 内容種別 | 手順的／概念的／参照的／物語的（時系列）／データ中心 | 本論の展開パターンを決める（時系列、問題→解決、原因→結果、比較対照、分類、一般→具体） |
| 5 | 専門性 | 初学者／中級／専門家 | 前提説明・用語定義・例の量と、詳細へ進む速さを決める |
| 6 | 寿命・形式性・媒体・分量 | 一時連絡か長期参照か／社内か社外か、上位者宛か、公的か／メール、Wiki、PDF、Web／上限字数 | 文体（敬体か常体か）、メタ情報欄、要約や目次の有無、圧縮の度合いを決める |

### 2.2 決定木

```
Q0 組織・法令・媒体の指定書式があるか？
  はい → 指定書式を骨格に採用。Q2以降で中身を調整
Q1 読者は読後に何をするか？
  承認・決定する
    金額・権限の決裁 → 稟議書／決裁文書
    新規施策の採否 → 企画書・提案書（PREP/SCQA）→ 長文なら Amazon型ナラティブ／PR/FAQ
    技術方式の合意 → デザインドキュメント／RFC
    決定済み事項の記録 → ADR
  報告を受ける
    進捗・調査結果 → 報告書（SDS）／障害 → ポストモーテム
    会議 → 議事録（決定事項先頭）／変更 → リリースノート
  作業する
    1つの目標達成 → ハウツー／手順書／障害対応・定常運用 → ランブック
    製品全体の操作 → マニュアル（タスク別章立て）
  学ぶ → 手を動かして習得：チュートリアル／体系的知識：教材の章
  調べる → 仕様・API：リファレンス／要件：要件定義書／よくある疑問：FAQ
  理解する → 概念・理由：解説記事／経験・知見：技術記事（Qiita/Zenn 型）
  動かされる → 周知：社内通知／依頼・説得：依頼メール（PREP）・訴求文（AIDA）
  検証する → 学術論文（IMRaD、Abstract で結論先出し）
  要点だけ知る → エグゼクティブサマリー／1枚もの（BLUF）
Q2 結論の位置
  既定：冒頭（結論ファースト／BLUF／PREP／SDS）
  状況が共有されていない・反対が予想される → SCQA（答えは冒頭1段落以内）
  学習順序に意味がある → 冒頭は完成像と学習目標、本論は積み上げ
  論文 → Abstract に結論、本文は IMRaD の順
Q3 専門性
  初学者 → 前提・用語定義・概念→例の順。前提条件セクションを独立
  専門家 → 結論・差分・詳細へ直行。背景は1段落か付録へ
Q4 媒体・分量
  メール・チャット → 件名で要件、冒頭で結論と依頼事項
  Web・Wiki → H2 を目次として機能させる
  上限字数あり → 第2階層以下を削り、第1階層の骨子は保つ
```

### 2.3 選択マトリクス（入力 → 推奨構成）

| 読者の目的 | 読者・姿勢 | メッセージ種別 | 第1候補 | 第2候補 | 選択理由 |
|---|---|---|---|---|---|
| 承認する | 経営層・冒頭だけ | 提言 | エグゼクティブサマリー＋稟議書 | 企画書（PREP） | 決裁者は金額・効果・リスクを所定の位置で探す |
| 承認する | 管理職・通読 | 提言 | 企画書・提案書（SCQA→提案→根拠） | Amazon 型ナラティブ | 状況の共有が必要な新規施策 |
| 合意する | エンジニア・通読 | 比較評価 | デザインドキュメント | RFC | 目標・非目標・代替案の明示が合意の前提 |
| 記録を残す | 将来のメンバー・検索 | 意思決定の記録 | ADR | デザインドキュメントの代替案節 | 1決定1記録で時点の文脈を保存 |
| 報告を受ける | 上司・拾い読み | 事実の報告 | 報告書（SDS） | エグゼクティブサマリー | 要点→詳細→要点で全体像を渡す |
| 報告を受ける | 関係者・通読 | 事実と再発防止 | ポストモーテム | 障害報告書（社外向け） | 影響・原因・対策を定位置に置く |
| 作業する | 実務者・拾い読み | 手順の指示 | ハウツー／手順書 | ランブック | 目標達成への最短経路 |
| 学ぶ | 初学者・通読 | 教育 | チュートリアル | 教材の章 | 成功体験を優先し説明は最小限 |
| 学ぶ | 学生・通読 | 教育 | 教材の章（目標→概念→例→演習→まとめ） | 解説記事 | 教授事象の順序に沿う |
| 調べる | 実務者・検索 | 事実 | リファレンス | FAQ | 製品の構造に沿った一貫した並び |
| 理解する | 中級者・通読 | 概念の説明 | 解説記事 | 技術記事 | 「なぜ」に答える |
| 知見を得る | 開発者・拾い読み | 主張と経験 | 技術記事（結論→背景→方法→結果→まとめ） | ハウツー | 冒頭で関係の有無を判断させる |
| 動かされる | 社員全体・冒頭だけ | 周知 | 社内通知（標題で性格を示し要点→詳細） | FAQ 付き通知 | 行動と期限を最初に示す |
| 動かされる | 社外・通読 | 依頼 | 依頼メール（PREP） | 提案書 | 依頼事項と期限を冒頭に |
| 検証する | 研究者・モジュール読み | 主張と証拠 | IMRaD 論文 | 短報 | 定位置で情報を拾える |

## 3. 構成カタログ（ジャンル別骨子）

各ジャンルについて、適用条件／骨子（日本語見出し・役割・目安分量）／メッセージの位置／アンチパターン／日本語での慣習を示します。分量の目安は本レポートの経験則で、一次情報で規定されている数値はその旨を明記しています。

### 3.1 技術ドキュメント系

**チュートリアル**
- 適用：初学者が手を動かして初めて成功するための文書。ハウツーとの違いは、読者がまだ「何がわからないかもわからない」こと（Diátaxis）。
- 骨子：はじめに（作るもの・完成像・所要時間、5%）→ 学習目標（3項目程度）→ 前提条件と準備 → ステップ1〜n（各ステップに「操作→結果の確認」、70%）→ 動作確認 → まとめ（学んだこと）→ 次のステップ
- メッセージ：冒頭に完成像を示し、本論は積み上げる。
- アンチパターン：説明を詰め込み、手順の流れを止める（Diátaxis が典型的な失敗として挙げている）。
- 日本語：敬体。見出しは「〜を作成する」のように動作名詞か動詞の形にする。

**ハウツー／手順書**
- 適用：目標を持つ実務者が特定の課題を解く文書。
- 骨子：概要（達成できること、1〜2文）→ 前提条件 → 手順（番号付き、1ステップ1操作）→ 結果の確認 → トラブルシューティング（任意）→ 関連情報
- メッセージ：冒頭（何ができるか）。
- アンチパターン：概念の説明や網羅的なオプション一覧を混ぜる（リファレンスと解説へ回す）。
- 日本語：手順は「〜します」か「〜する」で統一し、1文に1操作とする。

**ランブック**（一次情報未確認・一般的な実務慣行）
- 骨子：対象アラートとサービス → 影響と緊急度の判断基準 → 初動手順 → 診断手順 → 復旧手順 → エスカレーション先 → 事後作業 → 更新履歴
- メッセージ：冒頭（このページを使う条件）。アンチパターン：背景説明が長く、初動手順が埋もれる。

**リファレンス／API ドキュメント**
- 適用：検索して事実を確かめる読者向け。Diátaxis によれば、リファレンスはユーザーのニーズではなく、記述対象である製品の構造に従って組み立てる。
- 骨子（1項目あたり）：名前 → 概要（1文）→ 構文・シグネチャ → パラメーター（表）→ 戻り値 → エラー → 例 → 関連項目
- メッセージ：各項目の冒頭に1文の要約。アンチパターン：教えようとする（使い方の物語を混ぜる）。
- 日本語：常体か体言止めの表形式が読みやすい。

**解説記事（explanation）**
- 適用：「なぜそうなっているか」を理解したい読者向け。
- 骨子：導入（問い・この記事でわかること）→ 背景 → 中心概念 → 仕組み・理由 → 比較・トレードオフ → よくある誤解 → まとめ → 参考
- メッセージ：冒頭で答えの要旨を示し、本論で展開する。アンチパターン：手順を混ぜる、結論が出てこない。

**技術記事（Qiita/Zenn 型）**
- 適用：開発者が経験や知見を共有する記事。拾い読みする読者に「自分に関係あるか」をすぐ判断させる。
- 骨子：はじめに（結論・対象読者・前提環境とバージョン、10%）→ 背景・課題 → やったこと・方法 → 結果 → ハマりどころ・注意点 → まとめ → 参考文献
- メッセージ：冒頭（TL;DR かまとめを先に）。アンチパターン：経緯の日記になる、環境やバージョンを書かない。
- 備考：Qiita/Zenn の慣習は一次情報を確認できておらず、プラットフォームの公式規定ではなく実務上の慣行として扱う。

**デザインドキュメント**
- 適用：解決策があいまいで、組織の合意が必要な技術判断。
- 骨子（Google 型）：メタ情報（作成者・状態・レビュアー）→ 背景とスコープ → 目標と非目標 → 概要（提案の要旨）→ 詳細設計（システム構成図・API・データ）→ 横断的関心事（セキュリティ・プライバシー・可観測性）→ 検討した代替案 → 未解決事項
- メッセージ：「概要」で提案を先に示す。アンチパターン：非目標がない（スコープが際限なく広がる）、代替案が形だけ。
- RFC は統一された一次情報がなく、プロジェクトごとにテンプレートが異なるため、この骨子を基本形としてよい。

**ADR（Nygard 形式）**
- 適用：重要なアーキテクチャ上の決定を1件ずつ記録する。
- 骨子：タイトル（決定内容を表す短い名詞句）→ ステータス（提案／承認／廃止／置換）→ コンテキスト（決定を迫る力学）→ 決定（「〜を採用する」と能動的に）→ 結果（良い・悪い・中立的な影響）
- 分量：1〜2ページ。メッセージ：タイトルと「決定」。
- アンチパターン：複数の決定を1件にまとめる、置き換えられた ADR を削除する（Nygard は削除せず置換と記録することを勧めている）。

**要件定義書・仕様書**
- 適用：開発の前提となる合意事項を参照するとき。
- 骨子：文書の目的と範囲 → 用語定義 → 業務要件（業務内容・手順・ルール・業務用語・外部環境）→ 組織と環境の要件 → 機能要件（機能間のデータの流れ・人とシステムの分担・外部インタフェース）→ 非機能要件（品質・技術・運用と操作・移行・付帯作業・その他）→ 前提・制約 → 未決事項
- 根拠：IPA『共通フレーム2013』（2013年3月）の要件定義プロセスが定める分類。ただし共通フレームは文書の種類や書式を規定しないため、上の目次は分類に基づく推奨形で、公式テンプレートではない。IPA『ユーザのための要件定義ガイド 第2版』（2019年）は、成果物を「要件定義ドキュメント群」として扱っている（第7章 DD.1 ビジネスコンセプト〜DD.13 運用・移行・総合テストの要求）。
- アンチパターン：要求（なぜ）と仕様（何を）が混在する、非機能要件が抜ける。

**マニュアル**
- 骨子：はじめに（対象読者・本書の使い方・表記規則）→ 安全上の注意（該当時）→ 概要（全体像）→ 準備 → 基本操作（タスク別）→ 応用操作 → 困ったとき → 仕様・付録 → 索引
- アンチパターン：画面や機能の順に並べる（読者がやりたいタスクの順に並べる）。
- 日本語：JTCA『日本語スタイルガイド』の表記規則に従うと一貫性を保ちやすい。

**FAQ**
- 骨子：カテゴリ別の Q&A（問いは読者の言葉で書き、答えの1文目で結論を言う）→ 解決しない場合の問い合わせ先
- アンチパターン：実際には誰も聞かない質問、本来はハウツーにすべき長い手順の詰め込み。

**リリースノート**
- 骨子：バージョンと日付 → ハイライト（1〜3行）→ 破壊的変更と必要な対応（最上位）→ 新機能 → 改善 → バグ修正 → 既知の問題 → 非推奨と削除予定
- メッセージ：読者が対応を必要とする変更を先頭に置く。

### 3.2 学術・教育系

**学術論文（IMRaD）**
- 骨子：表題 → 要旨（背景・目的・方法・結果・結論）→ 序論（背景→未解決の問題→目的）→ 方法 → 結果 → 考察（主要な知見→先行研究との比較→限界→意義）→ 結論 → 謝辞 → 参考文献
- メッセージ：表題と要旨で結論を先に示し、本文は検証の順に積み上げる。
- 根拠：Sollaci & Pereira（2004, *J Med Libr Assoc* 92(3):364–367）によれば、IMRaD は調査対象誌で1940年代に使われ始め、過半数に採用されたのは1970年代になってからで、「モジュール読み」を容易にする（"The IMRAD structure facilitates modular reading"）。木下も、著者抄録で結論・研究の目的・研究法を明示し、序論は読者を最短経路で本論へ導くよう求めている。
- 日本語：常体（である調）。投稿先学会の投稿規定が最優先（Q0）。
- アンチパターン：結果と考察を混同する、序論が長い研究史になる。

**教科書・教材の章**
- 骨子：章の導入（なぜ学ぶか・問いかけ）→ 学習目標 → 前提の確認（既習事項）→ 本文（概念→例→図解の繰り返し）→ 例題 → 演習問題 → まとめ → 発展・次章への接続
- 根拠：Gagné の9教授事象（注意喚起／学習目標の提示／既習事項の想起／内容の提示／学習の指針／練習の機会／フィードバック／評価／保持と転移の促進）の順序に対応させた。原典は Gagné『The Conditions of Learning』（初版1965年）。

### 3.3 ビジネス文書系

**報告書（SDS 型）**
- 骨子：標題（「〜に関する報告」と文書の性格を明示）→ 要旨（結論・要点を3行程度）→ 背景・目的 → 経過・実施内容 → 結果 → 考察・課題 → 今後の対応 → 添付資料
- メッセージ：冒頭と末尾の両方。
- 報告書と企画書の違い：報告書は事実を渡して理解させる（SDS）。企画書は判断と行動を求める（PREP・SCQA）。
- アンチパターン：時系列の日誌になり、結論が最後まで出ない。

**企画書・提案書**
- 骨子：提案の要旨（何を・いくらで・何が得られるか）→ 現状と課題（SCQA の S と C）→ 提案内容 → 期待効果（定量）→ 実施計画・体制 → 費用 → リスクと対策 → 代替案との比較 → お願いしたい判断
- メッセージ：冒頭。アンチパターン：課題の説明に紙幅を使い切り、判断してほしい事項がない。

**エグゼクティブサマリー／1枚もの**
- 骨子：結論・提言（1〜2文、BLUF）→ 根拠3点（ピラミッドの第2階層、MECE）→ 必要な判断・期限 → 主要数値 → 詳細資料への参照
- 分量：A4で1枚。アンチパターン：本文を縮めただけの要約（結論がない）。

**Amazon 型ナラティブ（6ページャー）・PR/FAQ**
- 適用：重要な意思決定を文章による深い検討で行うとき。会議の冒頭で黙読される前提で書く。
- PR/FAQ：将来の発表日付のプレスリリース（1ページ未満）と FAQ（5ページ以内）。この分量の上限は、『Working Backwards』の著者で元 Amazon 社員の Colin Bryar と Bill Carr による規定（About Amazon 掲載の書籍抜粋：PR は "always less than one page"、FAQ は "five pages or less"）。
- 汎用ナラティブ：目的（何を議論し決めたいか）を先頭に置き、その後は目的に合わせて組み立てる。四半期レビューの例は「導入／原則／成果／未達／次期の提案／人員／損益／FAQ」。

**議事録**
- 骨子：会議名・日時・場所・出席者 → 決定事項 → 宿題事項（担当・期限）→ 議題ごとの討議要旨 → 次回予定
- メッセージ：決定事項と宿題を冒頭に。アンチパターン：発言の逐語的な羅列、決定と意見の区別がない。
- 日本語：公用文の考え方は議事録を「記録・公開資料等」に分類し、公用文表記を基本としつつ読み手に合わせた工夫を認めている。

**稟議書・決裁文書**
- 骨子：件名（対象＋行為＋目的。「〜について」で終わらせない）→ 起案者・起案日 → 決裁を求める事項（結論）→ 目的 → 理由・背景 → 実施内容 → 金額と内訳 → 期待効果 → リスクと対策 → スケジュール → 添付資料（見積・比較表）
- メッセージ：件名と「決裁を求める事項」。
- 根拠：単一の公的標準はなく、社内様式が最優先（Q0）。上の項目は複数の実務解説で共通しているもの。
- アンチパターン：目的が部署の都合になっている、代替案や比較がない。

**プロジェクト計画書**（一次情報未確認・一般的な実務慣行）
- 骨子：目的と成功基準 → スコープ（含む・含まない）→ 成果物 → スケジュールとマイルストーン → 体制と役割 → 予算 → リスク管理 → コミュニケーション計画 → 変更管理

**障害報告書・ポストモーテム**
- 骨子（Google SRE 本のテンプレートに準拠）：表題（インシデント番号）→ 日付・作成者・ステータス → 要約 → 影響 → 根本原因 → トリガー → 解決 → 検知 → アクションアイテム（担当・期限）→ 教訓（うまくいったこと・うまくいかなかったこと・運が良かったこと）→ タイムライン
- アクションアイテムは「調査・緩和・修復・検知・予防」に分類し、少なくとも緩和と予防を含める（Google SRE の Lunney ほか、USENIX ;login: 2017年春号）。
- アンチパターン：非難の物語になる、オーナーのいない対策。
- 日本語：社外向けの障害報告では、冒頭にお詫びと影響範囲を置き、技術的詳細は後段に回す。

**社内通知・案内**
- 骨子：標題（「〜の変更について（お知らせ）」のように性格を明示）→ 要点（誰が・何を・いつまでに）→ 詳細（「記」以下に箇条書き）→ 問い合わせ先
- 日本語：公用文の考え方の「標題で主題と文書の性格を示す」「三つ以上の情報は箇条書」「『下記』『別記』を適切に活用」がそのまま使える。

**依頼・説得メール**
- 骨子：件名（要件と期限）→ 宛名・挨拶（1行）→ 結論：依頼事項 → 理由・背景 → 具体的にお願いしたいこと（箇条書き・期限）→ 結び
- 型：判断や行動を求めるなら PREP、情報共有なら SDS（日本の実務解説で共通する使い分け）。訴求文には AIDA（注意→関心→欲求→行動）。
- アンチパターン：前置きの挨拶が長く、依頼が3段落目に出てくる。

## 4. 日本語文書特有の構成慣習と根拠

- **結論の位置**：「公用文作成の考え方」（2022年）は「結論は早めに示し、続けて理由や詳細を説明する」としている。日本語の文章は結論を出し渋る、という通念への公的な是正と読める。木下の重点先行主義も同じ立場をとる。
- **起承転結と序論・本論・結論**：起承転結は漢詩に由来する修辞構成で、仕事の文書には使わない。本スキルの既定は「序論（要旨を含む）→本論→結論」か結論ファーストとする。序論の役割は木下の整理に従い、①読むべきかどうかの判断材料を示し、②本論に必要な予備知識を与える、の2点に限る。
- **PREP 法・SDS 法**：PREP は「結論→理由→具体例→結論」、SDS は「要点→詳細→要点」。複数の日本語の実務解説が、判断や行動を求めるなら PREP、理解と情報共有なら SDS という使い分けで一致している。ただし単一の原典がない実務慣習である。
- **文体**：公用文の考え方では、法令・告示・訓令などは常体、通知・依頼・照会・回答など特定の相手に向けた文書は敬体とし、1文書内ではどちらかに統一する。対外的な文書は「です・ます」体が基本。スキルでは、論文・リファレンス・仕様書・ADR を常体、それ以外を敬体の既定とする。
- **標題と見出し**：標題で「主題」と「文書の性格」（報告、提案、回答、確認、開催、許可など）を示す。見出しを追えば全体の内容がつかめるようにし、標題と見出しを呼応させる。項目の階層は「第1 → 1 → (1) → ア → (ア)」（横書きの例）。
- **読み手の分類**：公用文の考え方は読み手の想定で文書を分類する（法令、告示・通知等＝専門的な知識がある人／記録・公開資料等＝ある程度の専門知識がある人／解説・広報等＝専門的な知識を特に持たない人）。一般向けの文書は義務教育で学ぶ範囲の知識で理解できるように書く。この分類は専門性の軸の目安になる。
- **分量**：「分量の限度を決めておく」「伝えることを絞る。副次的な内容は、別に対応する」（公用文の考え方）。本論から外れる内容を付録か別文書へ回す根拠になる。
- **テクニカルライティング**：JTCA（テクニカルコミュニケーター協会）の TC技術検定3級は、試験範囲に「対象理解とコンテキストの組み立て」「読み手を考えたライティング技術」を含む。JTCA『日本語スタイルガイド（第3版）』は、取扱説明書に限らず実用文全般に応用できるライティング指針として位置づけられている。

## 5. ハイブリッド・逸脱の指針と品質チェックリスト

### 5.1 ハイブリッドの指針

- **主目的は1つ、副目的は区画に分ける**：技術記事で手順も示したいなら「はじめに（結論）→背景（解説）→手順（ハウツー区画）→結果→まとめ」とし、区画の見出しで型の切り替わりを示す。Diátaxis の原則どおり、1区画に2つの型を混ぜない。
- **意思決定文書の前にサマリーを付ける**：長い企画書、デザインドキュメント、報告書は「エグゼクティブサマリー＋本体」の二層構成を既定とする。
- **定型と結論ファーストを両立させる**：定型の骨格は崩さず、定型の先頭欄（件名・要約・決裁を求める事項）に結論を入れる。
- **リファレンスとチュートリアルは原則として分ける**：同じ文書に入れるなら、別の H2 に分けて相互にリンクする。

### 5.2 定番から逸脱してよい条件

1. 読者の目的が定番の想定と明らかに違う（例：社外向けのポストモーテムでは、お詫びと影響を先に置く）。
2. 分量の制約で定番の全セクションを保てない（第2階層を統合し、第1階層の順序は保つ）。
3. 該当するセクションの内容が存在しない（「該当なし」と1行書くか削除する。定型文書では残す）。
4. 組織の指定書式と定番が衝突する（指定書式が優先）。

逸脱したら、出力の「選択理由」に逸脱点と理由を書くことを必須にします。

### 5.3 構成の品質チェックリスト

- [ ] 標題だけで主題と文書の性格がわかるか
- [ ] 主要メッセージ（結論・依頼・決定）が冒頭3文（または最初の段落）以内にあるか。積み上げ型なら、完成像か目標が冒頭にあるか
- [ ] 見出しだけを順に読んで筋が通るか。標題と見出しは呼応しているか
- [ ] 各セクションの目的が1つか（手順と概念、事実と意見が混在していないか）
- [ ] 同じ階層の見出しは MECE か。粒度はそろっているか
- [ ] 読者の目的に関係のない章がないか（副次的な内容は付録か別文書へ）
- [ ] 冒頭で範囲・前提・扱わないことを宣言しているか（長文の場合）
- [ ] 意思決定文書に代替案・非目標・リスクがあるか
- [ ] 報告・記録の文書で事実と意見が区別されているか
- [ ] 定型ジャンルの必須セクションが欠けていないか
- [ ] 文体（敬体か常体か）は文書内で統一され、ジャンルの既定に合っているか
- [ ] 分量の配分が本論中心になっているか（序論が全体の2割を超えていないか）

## 6. Microsoft APM 形式の仕様まとめ

### 6.1 「Microsoft APM」とは

- microsoft/apm として公開されている **Agent Package Manager**。AI エージェント用の依存関係マネージャーで、「エージェントのコンテキストにとっての npm」にあたる。スキル、プロンプト、インストラクション、エージェント、フック、プラグイン、MCP サーバーを `apm.yml` に宣言し、`apm install` で各ハーネス（GitHub Copilot、Claude Code、Cursor、Codex、Gemini、OpenCode、Windsurf、Kiro など）に配置する。`apm.lock.yaml` が解決結果を内容ハッシュつきで固定する。AGENTS.md、Agent Skills、MCP というオープン標準の上に構築されている。Agent Skills については、aq.dev の用語集（二次情報）によれば、Anthropic が2025年12月18日に agentskills.io でオープン標準として公開し、仕様・リファレンス検証ライブラリ・サンプルスキルの公開リポジトリが用意された。
- 他の候補：同名の Microsoft 製の文書形式は見つからなかったため、「APM 形式」は Agent Package Manager のパッケージ形式を指すと判断してよい。

### 6.2 パッケージ構造

- **最小構成**：`apm.yml` と `.apm/skills/<name>/SKILL.md`。
- **`apm.yml` の必須フィールド**：`name`（パッケージ名）と `version`（SemVer 文字列）の2つだけ。数値と解釈されないよう version は引用符で囲む。
- **任意フィールド**：`description`、`author`（文字列か `{name, email, url}`）、`license`、`homepage`、`repository`、`keywords`、`type`（`instructions`／`skill`／`hybrid`／`prompts` のいずれかで `.apm/` の中身を制約）、`targets`（YAML のリスト）、`includes`、`dependencies`（`apm`／`mcp`）、`devDependencies`、`scripts`。
- **`.apm/` 配下**：`instructions/`（`*.instructions.md`）、`skills/`、`prompts/`（`*.prompt.md`）、`agents/`（`*.agent.md`）、`context/`、`hooks/`。`.github/`、`.claude/`、`AGENTS.md` などは生成物なので直接編集しない。
- **単一スキルのリポジトリ**：ルートに `SKILL.md` を置く形も認められている（`apm.yml` を併置すると hybrid パッケージ）。この場合はディレクトリ全体が1つのスキルとして配置される。

### 6.3 スキルの扱い

- APM 公式ドキュメントは、APM はスキルの仕様ではなくパッケージマネージャーであり、SKILL.md の形式は Agent Skills 標準に従うと明言している。
- **フォルダ**：`.apm/skills/<name>/` に `SKILL.md`（必須）と任意の `scripts/`、`references/`、`assets/`、`examples/` を置く。インストール時にはフォルダごとコピーされる。
- **`name`**：agentskills.io の Specification（GitHub の agentskills/agentskills リポジトリ、docs/specification.mdx）の規定では、1〜64字（"Must be 1-64 characters"）、小文字の英数字（a-z、0-9）とハイフンのみ使用可、ハイフンの連続（--）は不可（"Must not contain consecutive hyphens"）、先頭・末尾のハイフンも不可、親ディレクトリ名と一致させる（"Must match the parent directory name"）。APM では、不一致の場合はディレクトリ名が優先される。
- **`description`**：1024字以内。APM の推奨は、命令形で始める（「〜のときに使う」）、ユーザーの意図を最初に書く（ランタイムは1文目でマッチングする）、スラッシュコマンドではなく状況を書く、の3点。
- **Agent Skills 標準の frontmatter**：使えるキーは `name`、`description`、`license`、`compatibility`、`metadata`、`allowed-tools` の6つで、必須は `name` と `description`。移植性のため、これ以外のキーは使わない。
- **段階的開示**：agentskills.io の Agent Skills Specification によれば、起動時には全スキルの name と description だけ（"Metadata (~100 tokens)"）が読み込まれ、SKILL.md 本文は有効化時に読み込まれる（"Instructions (< 5000 tokens recommended)"）。`references/` は必要なときだけ読み込まれる。APM は本文を500行・5000トークン以内に収め、はみ出した分を `references/<topic>.md` に移して本文中に「LOAD references/<file>」と書く方式を推奨している。
- **配置先**：`claude` は `.claude/skills/<name>/`、`kiro` は `.kiro/skills/`、`grok-build` は `.grok/skills/`。`copilot`、`cursor`、`codex`、`gemini`、`opencode`、`windsurf` は `.agents/skills/<name>/`。
- **検証**：`apm install --dry-run --target claude` で配置先をプレビューし、`apm audit --file .apm/skills/<name>/SKILL.md` で不可視 Unicode などを検査する。
- **インストラクションとの組み合わせ**：`.apm/instructions/*.instructions.md` の frontmatter は `description`（必須）と `applyTo`（glob、任意）。`applyTo` があればそのファイル群に紐づけて配置され、なければコンパイル済みのコンテキストファイル（AGENTS.md など）に常時読み込まれる。ハーネス側で常にスキル利用を促したい場合だけ、`applyTo: "docs/**/*.md"` のインストラクションで「本文を書く前に jp-doc-structure で骨子を決める」と指示すればよい。

```markdown
# 日本語文書の構成選択

## 目的
与えられた目的・読者・メッセージ・内容から文書構成を1つ選び、本文執筆の前に使う「骨子」を出力する。事実は整理済み、論理は検証済みとして扱い、内容の追加や論証の修正はしない。

## 1. 入力の受け取り方
ハーネスから次の項目を受け取る。欠けている項目は（ ）内の既定値で補い、出力の「仮定」欄に明記する。
- 目的：読者が読後に何をするか（決める／報告を受ける／作業する／学ぶ／調べる／理解する／動かされる／検証する）
- 読者：役割、専門性（初学者／中級／専門家。既定は中級）、読む姿勢（通読／拾い読み／冒頭だけ。役職者は冒頭だけ）
- メッセージ：中心となる主張・結論（1〜2文）と種別（提言／決定の記録／事実報告／手順指示／概念説明／比較評価／教育）
- 内容：手順的／概念的／参照的／時系列／データ中心、および主要な要素の一覧
- 制約：指定書式、媒体（メール／Wiki／Web／PDF）、分量上限、社内か社外か（既定は社内・Web）

## 2. 判断手順
1. **定型の確認**：組織の様式・投稿規定・法令書式が指定されていればそれを骨格とし、手順4以降で中身を調整する。
2. **系統の決定**：目的からジャンルの候補を2つ選ぶ。LOAD references/decision-rules.md（決定木と選択マトリクス）
3. **型の決定**：メッセージ種別で型を確定する（判断を求めるなら PREP か SCQA、報告なら SDS、決定の記録なら ADR、学術なら IMRaD）。
4. **結論の位置**：既定は冒頭（結論ファースト）。次の場合だけ変える。
   - 学習順序に意味がある → 冒頭に完成像と学習目標、本論は積み上げ
   - 状況が共有されていない、または反対が予想される → SCQA で状況と複雑化を短く述べ、答えは第1段落内に置く
   - 論文 → 要旨に結論、本文は IMRaD の順
   - 起承転結（「転」で話題を転じる構成）は使わない
5. **深さの調整**：初学者向けなら前提条件・用語定義・例を独立したセクションにする。専門家向けなら背景を1段落か付録にまとめる。
6. **媒体と分量への適合**：メールなら件名で要件、冒頭で結論と依頼を示す。Web なら H2 を目次として機能させる。分量の上限があれば第2階層を統合し、第1階層の順序は保つ。
7. **骨子の作成**：該当するカタログを読み込み、定番骨子を入力内容に合わせて具体化する。
   - 技術系：LOAD references/catalog-technical.md
   - 論文・教材：LOAD references/catalog-academic-edu.md
   - ビジネス系：LOAD references/catalog-business.md
   - 文体・標題・見出しの規則：LOAD references/japanese-conventions.md
   - 目的が複数、または定番から外れる場合：LOAD references/hybrid-and-checklist.md

## 3. 出力形式
次の Markdown で出力する。見出しは内容を表す具体的な名詞句か文にし、「その他」「概要2」のような見出しは使わない。

    ## 構成選択結果
    - 採用構成：<ジャンル名>（型：<PREP/SDS/SCQA/IMRaD/Diátaxis種別 等>）
    - 第2候補：<ジャンル名> — 採用しなかった理由：<1文>
    - 選択理由：<読者の目的・読む姿勢・メッセージ種別にどう対応するか 2〜3文>
    - 核メッセージの位置：<冒頭/末尾/両方> — <どのセクションの何文目か>
    - 文体：<敬体/常体>　標題案：<主題＋文書の性格>
    - 仮定・逸脱：<補った入力、定番からの逸脱とその理由>

    ## 骨子
    1. <見出し>（役割：<1文>／目安：<字数または割合>）
       - 入れる要素：<入力内容のどれを置くか>
    2. ...

    ## 構成チェック
    - [x]/[ ] 各項目（下記5.の結果）

## 4. 原則
- 1文書1主目的。目的が2つあるときは区画に分けるか、文書の分割を提案する。
- 1セクション1目的。手順と概念、事実と意見を同じセクションに混ぜない。
- 標題で主題と文書の性格（報告・提案・依頼・お知らせなど）を示す。
- 見出しだけで筋が通るようにする。同じ階層の見出しは MECE で、粒度をそろえる。
- 定型ジャンルでは必須セクションを削らない（該当しない場合は「該当なし」と書く）。

## 5. 最終チェック
出力前に確認し、結果を「構成チェック」に記す。
- 主要メッセージが冒頭3文以内にあるか（積み上げ型なら、完成像か目標が冒頭にあるか）
- 見出しだけで筋が通るか。標題と見出しが呼応しているか
- 各セクションの目的が1つか。同じ階層の見出しが MECE か
- 読者の目的に不要な章がないか。範囲・前提・扱わないことを宣言しているか（長文の場合）
- 意思決定文書に代替案・リスク・判断事項があるか。定型の必須セクションがそろっているか
- 文体がジャンルの既定に合い、統一されているか
```

### 参照ファイルに分割する内容

- `references/decision-rules.md`：第2章（判断軸の表、決定木、選択マトリクス）をそのまま転記する。
- `references/catalog-technical.md`／`catalog-academic-edu.md`／`catalog-business.md`：3.1〜3.3 の各ジャンル。1ジャンルにつき「適用条件／骨子／メッセージの位置／目安分量／アンチパターン／日本語の慣習」の6項目に統一する。ビジネス版の冒頭には、報告書と企画書、ハウツーとチュートリアルなど似たジャンルの判別表を置く。
- `references/japanese-conventions.md`：第4章（結論の位置、起承転結を使わない理由、PREP と SDS、文体の選択表、標題と見出しの規則、階層記号、読み手の分類表）。
- `references/hybrid-and-checklist.md`：第5章（ハイブリッド、逸脱の4条件、チェックリスト全項目）。
- `examples/sample-outputs.md`：(a) 経営層向けのシステム導入稟議、(b) 初学者向けチュートリアル、(c) Zenn 向けの技術記事、の入力と出力の例。出力形式を安定させるために置く。

## Recommendations

1. **ハーネスの入力スキーマに「読者の目的」を必須項目として加える。** 構成選択を最も強く支配する軸なので、自由記述ではなく8値の列挙型で渡すと選択が安定します。
2. **最初から `.apm/skills/` の構成で作る。** 単一スキルならルートに SKILL.md を置く形でも動きますが、将来インストラクションや「本文執筆スキル」を追加しやすいのは `.apm/` 配下の構成です。
3. **description の1文目を「日本語ドキュメントの章立て・セクション順序を決めるときに使う」とする。** ランタイムは1文目でマッチングするため、ほかの文章系スキルとトリガーが衝突しないよう、「構成（マクロ構造）」に限定していることを明示します。
4. **`examples/` に入力と出力の例を3件以上入れる。** 出力形式の揺れを抑える効果が最も大きい追加物です。
5. **社内の定型（稟議書・議事録・障害報告など）がある組織では、`references/org-templates.md` を追加して Q0 で読み込ませる。** 公用文の考え方の「既存の形式によることを基本」と同じく、組織の定型を一般論より優先させるためです。公開前には `apm install --dry-run` と `apm audit --file` を実行してください。

## Caveats

- **確証の度合い**：公用文の考え方、Diátaxis、APM、Agent Skills 仕様、Google のデザインドキュメントとポストモーテム、ADR、IMRaD の調査論文、IPA の資料は、一次情報か作成者本人による記述で確認しました。PREP 法・SDS 法・稟議書の構成は複数の実務解説サイトで一致していますが、単一の原典はありません。Qiita/Zenn の慣習、ランブック、PRD、プロジェクト計画書、RFC の汎用骨子、AIDA、STAR、逆三角形、Bloom のタキソノミー、Divio と Write the Docs、Microsoft Learn の文書種別ごとのテンプレート、Minto 邦訳の書誌は一次情報を確認できておらず、一般的な実務知識として記述しています。
- **Amazon の情報**：PR/FAQ の分量（PR は1ページ未満、FAQ は5ページ以内）は、著者による書籍抜粋（About Amazon 掲載）に基づきます。四半期レビューの章立ては、書籍の読書メモ経由の二次情報です。
- **APM は変化が速い**：参照した APM ドキュメントは2026年10月時点のもので、Windsurf の `.agents/skills/` への統合など、配置先は最近も変わっています。実装時には公式の Targets matrix で最新の配置先を確認してください。
- **分量の目安**：各ジャンルの割合や字数は、一次情報で数値が示されている Amazon と Agent Skills 以外、本レポートの経験則です。ハーネスの評価データで調整してください。
