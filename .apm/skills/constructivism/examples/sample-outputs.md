# 入力→出力の例（3件）

SKILL.md 第3節の出力形式を安定させるための例。入力は本スキルを呼び出すハーネスが渡す項目（目的・読者・メッセージ・内容・制約）、出力は SKILL.md 第3節の形式に従う。題材（組織名・金額・数値・製品名）はすべて架空で、構成の選び方と理由付けはレポートの決定木・選択マトリクス・カタログに基づく。

## 例 (a) 経営層向けのシステム導入稟議書

### 入力（ハーネスから）

- 目的：決める（承認）。クラウド型経費精算システムの導入について決裁を得る。
- 読者：経営会議（社長・取締役）。専門性は中級（業務には詳しいが IT は専門外）。読む姿勢は未指定。
- メッセージ：「クラウド型経費精算システム X を年額 480 万円で導入し、経費処理工数を年 1,200 時間削減する。4月からの利用開始について承認をお願いしたい」。種別：提言。
- 内容：データ中心（効果試算・費用）と手順的（導入計画）。要素：紙ベース処理の現状と問題、3製品の比較表、見積、3か月の導入スケジュール、情報セキュリティ上のリスクと対策、期待効果の試算、導入体制。
- 制約：社内の稟議書様式あり（件名／起案者・起案日／決裁事項／目的／理由／金額／添付 の欄）。本文は A4 2枚以内、添付は別。PDF。社内。

### 出力

```markdown
## 構成選択結果
- 採用構成：エグゼクティブサマリー＋稟議書・決裁文書（型：結論ファースト。社内様式を骨格にし、先頭欄「決裁を求める事項」を要約として使う）
- 第2候補：企画書・提案書（PREP） — 採用しなかった理由：求められているのは新規施策の採否ではなく金額と権限の決裁であり、社内の稟議書様式が指定されているため。
- 選択理由：読者の目的は「承認する」、読者は経営層で読む姿勢は冒頭だけ、メッセージは提言。選択マトリクスの「承認する／経営層・冒頭だけ／提言」に当たり、第1候補はエグゼクティブサマリー＋稟議書。社内様式があるので（Q0）様式を骨格とし、定型の先頭欄に結論・金額・判断期限を入れて結論ファーストと両立させる。決裁者が金額・効果・リスクを所定の位置で探せるよう、様式の欄の順序は変えない。
- 核メッセージの位置：冒頭 — 件名と、「決裁を求める事項」の第1文
- 文体：敬体 標題案：経費精算システム X の導入決裁依頼（年額 480 万円・経費処理工数を年 1,200 時間削減）
- 仮定・逸脱：読む姿勢は未指定のため「役職者は冒頭だけ」の既定を適用した。A4 2枚の制約により、カタログの「実施内容」と「スケジュール」を1節に統合し（逸脱条件2）、3製品の比較表と見積は添付へ回して本文では結論だけ述べる。代替案の比較は本文「理由・背景」で1段落触れ、詳細は添付の比較表に置く。

## 骨子
1. 件名（役割：対象＋行為＋目的を1行で示す。「〜について」で終わらせない／目安：1行）
   - 入れる要素：システム X、導入の決裁依頼、年額 480 万円、年 1,200 時間削減
2. 起案者・起案日（役割：様式のメタ情報／目安：1行）
   - 入れる要素：起案部署・起案者名・日付
3. 決裁を求める事項（役割：結論。何を・いくらで・いつから、判断の期限と根拠3点を BLUF で示す／目安：3〜5文）
   - 入れる要素：X の導入承認、年額 480 万円（初期費用込みの5年総額）、4月利用開始、根拠3点（工数削減・決算早期化・統制強化）、経営会議での承認期限
4. 目的（役割：経営上の狙い。部署の都合ではなく会社の利益で書く／目安：2〜3文）
   - 入れる要素：経費処理工数の削減、月次決算の早期化、内部統制の強化
5. 理由・背景（役割：現状の課題と導入の必然性（SCQA の S と C）、他製品と比べて X を選ぶ理由／目安：本文の 20%）
   - 入れる要素：紙ベース処理の問題、処理時間の実測値、差し戻し件数、3製品比較の結論（詳細は添付）
6. 実施内容とスケジュール（役割：導入範囲と3か月の計画、体制／目安：本文の 15%）
   - 入れる要素：対象部門、月ごとのマイルストーン、推進体制
7. 金額と内訳（役割：年額・初期費用・5年総額を表で示す／目安：表1つ）
   - 入れる要素：見積の内訳、支払条件
8. 期待効果（役割：定量効果と投資回収／目安：本文の 15%）
   - 入れる要素：年 1,200 時間削減の算出根拠、人件費換算、回収期間
9. リスクと対策（役割：情報セキュリティ・データ移行・定着のリスクと対策／目安：本文の 15%）
   - 入れる要素：セキュリティチェックの結果、移行計画、研修
10. 添付資料（役割：本文の根拠となる資料の一覧／目安：一覧）
    - 入れる要素：見積書、3製品比較表、セキュリティチェックシート

## 構成チェック
- [x] 主要メッセージが冒頭3文以内にあるか（件名と「決裁を求める事項」の第1文）
- [x] 見出しだけで筋が通るか。標題と見出しが呼応しているか（件名の「導入」「480 万円」「1,200 時間」が目的・金額・期待効果の各節に対応）
- [x] 各セクションの目的が1つか。同じ階層の見出しが MECE か（理由と効果、効果とリスクを分けた）
- [x] 読者の目的に不要な章がないか。範囲・前提・扱わないことを宣言しているか（短文のため、対象部門と導入範囲を「決裁を求める事項」と「実施内容」で示す）
- [x] 意思決定文書に代替案・リスク・判断事項があるか。定型の必須セクションがそろっているか（代替案は「理由・背景」と添付の比較表、リスクは第9節、判断事項は第3節。社内様式の欄はすべて骨子に対応させた）
- [x] 文体がジャンルの既定に合い、統一されているか（敬体）
```

## 例 (b) 初学者向けのチュートリアル

### 入力（ハーネスから）

- 目的：学ぶ（手を動かして習得する）。
- 読者：プログラミング初学者（HTML を少し触った程度）。専門性は初学者。読む姿勢は通読。
- メッセージ：「Python と Flask を使って、ブラウザに『こんにちは』と表示する Web アプリを 30 分で動かせる」。種別：教育。
- 内容：手順的。要素：Python のインストール確認、仮想環境の作成、Flask のインストール、app.py の作成、開発サーバーの起動、ブラウザでの確認、ルートの追加、よくあるエラー（ポート競合、仮想環境の有効化忘れ）。
- 制約：社内の学習サイト（Web、Markdown）。分量上限なし。指定書式なし。

### 出力

```markdown
## 構成選択結果
- 採用構成：チュートリアル（型：Diátaxis のチュートリアル。冒頭に完成像と学習目標、本論は積み上げ）
- 第2候補：教科書・教材の章 — 採用しなかった理由：体系的な知識の習得ではなく、1つの Web アプリを動かす成功体験を得ることが目的のため。
- 選択理由：読者の目的は「学ぶ」、読者は初学者で通読、メッセージは教育。選択マトリクスの「学ぶ／初学者・通読／教育」に当たり、第1候補はチュートリアル。学習順序に意味があるので結論の位置は既定の冒頭から変え、冒頭に完成像と学習目標を置いて本論は積み上げる（Q2）。初学者向けに前提条件を独立したセクションにし、各ステップは「操作→結果の確認」で構成する（Q3）。
- 核メッセージの位置：冒頭 — 「はじめに」の第1文に完成像（ブラウザに表示される画面）と所要時間 30 分
- 文体：敬体 標題案：Flask で最初の Web アプリを作る（30 分チュートリアル）
- 仮定・逸脱：入力の「よくあるエラー」は独立した章にせず、該当ステップの「結果の確認」の直後に「うまくいかないとき」として 1〜2 行で置く（説明を詰め込んで手順の流れを止めないため）。見出しは「〜を作成する」のように動詞の形にそろえた。

## 骨子
1. はじめに（役割：作るもの・完成像・所要時間を示す／目安：5%）
   - 入れる要素：完成画面のスクリーンショット、所要時間 30 分、対象読者（HTML を触ったことがある人）
2. このチュートリアルで学ぶこと（役割：学習目標3項目／目安：3行）
   - 入れる要素：仮想環境を作れる、Flask アプリを起動できる、ルートを追加できる
3. 前提条件と準備（役割：必要な環境と確認方法／目安：5%）
   - 入れる要素：Python のインストール確認コマンド、ターミナルの開き方、作業フォルダの作成
4. ステップ1：仮想環境を作成する（役割：操作→結果の確認／目安：ステップ1〜5 で 70%）
   - 入れる要素：作成コマンド、有効化コマンド、プロンプトの変化で確認、うまくいかないとき（有効化忘れ）
5. ステップ2：Flask をインストールする（役割：操作→結果の確認）
   - 入れる要素：インストールコマンド、バージョン表示で確認
6. ステップ3：app.py を作成する（役割：操作→結果の確認）
   - 入れる要素：最小のコード全文、保存場所の確認
7. ステップ4：開発サーバーを起動してブラウザで確認する（役割：操作→結果の確認）
   - 入れる要素：起動コマンド、ブラウザに「こんにちは」が出る画面、うまくいかないとき（ポート競合）
8. ステップ5：ルートを1つ追加する（役割：操作→結果の確認）
   - 入れる要素：追加するコード、再読み込みで確認
9. 動作確認（役割：2つのルートが動くことを通しで確認する／目安：5%）
   - 入れる要素：確認手順のチェックリスト
10. まとめ（役割：学んだことの振り返り／目安：3行）
    - 入れる要素：学習目標3項目の再掲
11. 次のステップ（役割：次に読む文書への案内／目安：3行）
    - 入れる要素：テンプレートとフォーム入力のチュートリアルへのリンク

## 構成チェック
- [x] 主要メッセージが冒頭3文以内にあるか（積み上げ型のため、完成像と所要時間を「はじめに」の第1文に置いた）
- [x] 見出しだけで筋が通るか。標題と見出しが呼応しているか（標題の「最初の Web アプリを作る」に対し、ステップ1〜5 が作成手順の順になっている）
- [x] 各セクションの目的が1つか。同じ階層の見出しが MECE か（1ステップ1操作、概念の説明は入れない）
- [x] 読者の目的に不要な章がないか。範囲・前提・扱わないことを宣言しているか（前提条件を独立節にし、「はじめに」で対象読者を宣言）
- [x] 意思決定文書に代替案・リスク・判断事項があるか。定型の必須セクションがそろっているか（意思決定文書ではないため前半は該当なし。カタログの定番骨子の節はすべて含めた）
- [x] 文体がジャンルの既定に合い、統一されているか（敬体）
```

## 例 (c) Zenn 向けの技術記事

### 入力（ハーネスから）

- 目的：理解する（開発者に経験・知見を共有する）。
- 読者：Web バックエンド開発者。専門性は中級。読む姿勢は拾い読み。
- メッセージ：「GitHub Actions の CI を 12 分から 4 分に短縮できた。効いたのは依存関係のキャッシュとテストの並列化で、Docker レイヤーキャッシュはほとんど効かなかった」。種別：提言（主張と経験）。
- 内容：時系列とデータ中心。要素：対象リポジトリの規模と構成（Node.js 20、pnpm、Jest）、改善前の計測値、試した4施策（依存関係キャッシュ、テスト並列化、Docker レイヤーキャッシュ、ジョブ分割）とそれぞれの効果、設定ファイルの抜粋、ハマりどころ（キャッシュキーの設計）、参考リンク。
- 制約：Zenn（Web、Markdown）。分量の目安は 5,000 字。社外公開。指定書式なし。

### 出力

```markdown
## 構成選択結果
- 採用構成：技術記事（Qiita/Zenn 型）（型：結論ファースト。結論→背景→方法→結果→まとめ）
- 第2候補：ハウツー／手順書 — 採用しなかった理由：読者に手順を再現させることより、何が効いて何が効かなかったかという経験の共有が主目的のため。
- 選択理由：読者の目的は「理解する」のうち経験・知見の共有で、読者は開発者・拾い読み、メッセージは主張と経験。選択マトリクスの「知見を得る／開発者・拾い読み／主張と経験」に当たり、第1候補は技術記事。拾い読みする読者が冒頭で自分に関係あるかを判断できるよう、「はじめに」に結論・対象読者・前提環境とバージョンを置く。Web 媒体なので H2 を目次として機能させる。
- 核メッセージの位置：冒頭 — 「はじめに」の第1文（12 分→4 分と、効いた施策・効かなかった施策）。「まとめ」で再掲。
- 文体：敬体 標題案：GitHub Actions の CI を 12 分から 4 分に短縮した話：効いた施策と効かなかった施策
- 仮定・逸脱：設定ファイルの抜粋は「やったこと」の各施策の中に置き、手順書の区画は作らない（1区画に2つの型を混ぜない）。4施策は試した順ではなく効果の大きい順に並べる（時系列の日記にしないため）。Qiita/Zenn の慣習は実務上の慣行として扱う。

## 骨子
1. はじめに（役割：結論・対象読者・前提環境とバージョン／目安：10%）
   - 入れる要素：12 分→4 分、効いた施策2つと効かなかった施策、対象読者（GitHub Actions で Node.js の CI を回している人）、Node.js 20／pnpm／Jest のバージョン、記事執筆日
2. 背景・課題（役割：改善前の状態と計測／目安：15%）
   - 入れる要素：リポジトリの規模、改善前のジョブ別所要時間、ボトルネックの内訳
3. やったこと（役割：試した4施策を効果の大きい順に、設定抜粋と計測値つきで示す／目安：40%）
   - 入れる要素：3.1 依存関係のキャッシュ、3.2 テストの並列化、3.3 ジョブの分割、3.4 Docker レイヤーキャッシュ（効かなかった理由）
4. 結果（役割：改善前後の比較表／目安：10%）
   - 入れる要素：施策ごとの短縮時間、合計の before/after
5. ハマりどころ・注意点（役割：再現する読者が詰まる点／目安：15%）
   - 入れる要素：キャッシュキーの設計、ロックファイル更新時の挙動
6. まとめ（役割：結論の再掲と、どんなリポジトリに効くか／目安：5%）
   - 入れる要素：効いた施策・効かなかった施策の一覧、適用条件
7. 参考文献（役割：公式ドキュメントと参考記事へのリンク／目安：一覧）
   - 入れる要素：GitHub Actions のキャッシュに関する公式ドキュメント、Jest の並列実行に関する公式ドキュメント

## 構成チェック
- [x] 主要メッセージが冒頭3文以内にあるか（「はじめに」の第1文）
- [x] 見出しだけで筋が通るか。標題と見出しが呼応しているか（標題の「短縮」「効いた施策と効かなかった施策」が「やったこと」「結果」「まとめ」に対応）
- [x] 各セクションの目的が1つか。同じ階層の見出しが MECE か（施策の説明と結果の比較を分けた）
- [x] 読者の目的に不要な章がないか。範囲・前提・扱わないことを宣言しているか（「はじめに」で対象読者と前提環境を宣言）
- [x] 意思決定文書に代替案・リスク・判断事項があるか。定型の必須セクションがそろっているか（意思決定文書ではないため前半は該当なし。カタログの定番骨子の節はすべて含めた）
- [x] 文体がジャンルの既定に合い、統一されているか（敬体）
```
