# 入力→出力の例（3件）

SKILL.md 第3節の出力形式を安定させるための例。入力は本スキルを呼び出すハーネスが渡す項目（目的・読者・メッセージ・内容・制約）、出力は SKILL.md 第3節の形式に従う。題材（組織名・金額・数値・製品名）はすべて架空で、構成の選び方と理由付けはレポートの決定木・選択マトリクス・カタログに基づく。出力の「入れる要素」は入力にある要素だけを配置し、入力にない内容は足さない。

## 例 (a) 経営層向けのシステム導入稟議書

### 入力（ハーネスから）

- 目的：決める（承認）。クラウド型経費精算システムの導入について決裁を得る。
- 読者：経営会議（社長・取締役）。専門性は中級（業務には詳しいが IT は専門外）。読む姿勢は未指定。
- メッセージ：「クラウド型経費精算システム X を年額 480 万円で導入し、経費処理工数を年 1,200 時間削減する。4月からの利用開始に向け、3月の経営会議で承認をお願いしたい」。種別：提言。
- 内容：データ中心（効果試算・費用）と手順的（導入計画）。要素：紙ベース処理の現状と問題、3製品の比較表と X を選んだ理由、見積（年額の内訳）、3か月の導入スケジュール、導入体制、情報セキュリティ上のリスクと対策、期待効果の試算（年 1,200 時間削減の算出根拠）。
- 制約：社内の稟議書様式あり（件名／起案者・起案日／決裁事項／目的／理由／金額／添付 の7欄）。本文は A4 2枚以内、添付は別。PDF。社内。

### 出力

```markdown
## 構成選択結果
- 採用構成：エグゼクティブサマリー＋稟議書・決裁文書（型：結論ファースト。社内様式の7欄を骨格にし、先頭欄「決裁事項」を要約として使う）
- 第2候補：企画書・提案書（PREP） — 採用しなかった理由：求められているのは新規施策の採否ではなく金額と権限の決裁であり、社内の稟議書様式が指定されているため。
- 選択理由：読者の目的は「承認する」、読者は経営層で読む姿勢は冒頭だけ、メッセージは提言なので、選択マトリクスの「承認する／経営層・冒頭だけ／提言」に従いエグゼクティブサマリー＋稟議書を選んだ。社内様式があるため（Q0）様式の7欄を第1階層とし、先頭欄に結論・金額・判断期限を入れて結論ファーストと両立させる。逸脱として、カタログで独立している実施内容・期待効果・リスクと対策・スケジュールは様式にない欄なので「理由」欄の第2階層に置いた（指定書式が優先、逸脱条件4）。
- 核メッセージの位置：冒頭 — 件名と、「決裁事項」の第1文
- 文体：敬体 標題案：経費精算システム X の導入決裁依頼（年額 480 万円・経費処理工数を年 1,200 時間削減）
- 仮定・逸脱：読む姿勢は未指定のため「役職者は冒頭だけ」の既定を適用した。様式の7欄を第1階層とし、カタログで独立していた実施内容・期待効果・リスクと対策・スケジュールを「理由」欄の第2階層に配置した（逸脱条件4）。A4 2枚の制約により、実施内容とスケジュールは第2階層で1項目に統合し（逸脱条件2）、3製品の比較表と見積は添付へ回して本文では結論だけ述べる。

## 骨子
1. 件名（役割：対象＋行為＋目的を1行で示す。「〜について」で終わらせない／目安：40字）
   - 入れる要素：システム X、導入の決裁依頼、年額 480 万円、年 1,200 時間削減
2. 起案者・起案日（役割：様式のメタ情報／目安：20字）
   - 入れる要素：起案部署・起案者名・起案日
3. 決裁事項（役割：結論を BLUF で示す要約。何を・いくらで・いつから、根拠3点、判断の期限／目安：本文の 10%）
   - 入れる要素：X の導入承認、年額 480 万円、4月利用開始、根拠3点（年 1,200 時間の工数削減・3製品比較で X を選定・セキュリティリスクは対策済み）、3月の経営会議での承認
4. 目的（役割：経営上の狙い。部署の都合ではなく会社の利益で書く／目安：本文の 5%）
   - 入れる要素：経費処理工数の年 1,200 時間削減
5. 理由（役割：決裁を支える根拠を、現状→選定→実施→効果→リスクの順に第2階層で示す／目安：本文の 70%）
   - 5.1 現状と課題（SCQA の S と C）：紙ベース処理の現状と問題
   - 5.2 製品選定の理由：3製品比較の結論と X を選んだ理由（比較表は添付）
   - 5.3 実施内容とスケジュール：導入体制、3か月の導入スケジュール
   - 5.4 期待効果：期待効果の試算（年 1,200 時間削減の算出根拠）
   - 5.5 リスクと対策：情報セキュリティ上のリスクと対策
6. 金額（役割：年額と内訳を表で示す／目安：本文の 10%）
   - 入れる要素：見積に基づく年額 480 万円の内訳
7. 添付（役割：本文の根拠となる資料の一覧／目安：本文の 5%）
   - 入れる要素：見積書、3製品比較表

## 構成チェック
- [x] 主要メッセージが冒頭3文以内にあるか（積み上げ型なら、完成像か目標が冒頭にあるか）
  - 判定理由：件名と「決裁事項」の第1文に、結論・金額・開始時期がある
- [x] 見出しだけで筋が通るか。標題と見出しが呼応しているか
  - 判定理由：件名の「導入」「480 万円」「1,200 時間」が、目的・金額・理由（期待効果）の各欄に対応する
- [x] 各セクションの目的が1つか。同じ階層の見出しが MECE か
  - 判定理由：「理由」欄の第2階層を現状・選定・実施・効果・リスクに分け、重複をなくした
- [x] 読者の目的に不要な章がないか。範囲・前提・扱わないことを宣言しているか（長文の場合）
  - 判定理由：7欄すべてが決裁の判断に使われる。短文のため範囲は「決裁事項」と 5.3 で示す
- [x] 意思決定文書に代替案・リスク・判断事項があるか。定型の必須セクションがそろっているか
  - 判定理由：代替案は 5.2 と添付の比較表、リスクは 5.5、判断事項は「決裁事項」。様式の7欄はすべて含む
- [x] 文体がジャンルの既定に合い、統一されているか
  - 判定理由：敬体で統一
```

## 例 (b) 初学者向けのチュートリアル

### 入力（ハーネスから）

- 目的：学ぶ（手を動かして習得する）。
- 読者：プログラミング初学者（HTML を少し触った程度）。専門性は初学者。読む姿勢は通読。
- メッセージ：「Python と Flask を使って、ブラウザに『こんにちは』と表示する Web アプリを 30 分で動かせる」。種別：教育。
- 内容：手順的。要素：完成画面のスクリーンショット、Python のインストール確認、仮想環境の作成と有効化、Flask のインストール、app.py の作成（最小のコード）、開発サーバーの起動、ブラウザでの確認、ルートの追加、よくあるエラー（ポート競合、仮想環境の有効化忘れ）、次に学ぶ内容の候補（テンプレート、フォーム入力）。
- 制約：社内の学習サイト（Web、Markdown）。分量上限なし。指定書式なし。

### 出力

```markdown
## 構成選択結果
- 採用構成：チュートリアル（型：Diátaxis のチュートリアル。冒頭に完成像と学習目標、本論は積み上げ）
- 第2候補：教科書・教材の章 — 採用しなかった理由：体系的な知識の習得ではなく、1つの Web アプリを動かす成功体験を得ることが目的のため。
- 選択理由：読者の目的は「学ぶ」、読者は初学者で通読、メッセージは教育なので、選択マトリクスの「学ぶ／初学者・通読／教育」に従いチュートリアルを選んだ。学習順序に意味があるため結論の位置は既定の冒頭から変え、冒頭に完成像と学習目標を置いて本論は積み上げる（Q2）。初学者向けに前提条件を独立したセクションにし、各ステップは「操作→結果の確認」で構成する（Q3）。
- 核メッセージの位置：冒頭 — 「はじめに」の第1文（完成像と所要時間 30 分）
- 文体：敬体 標題案：Flask で最初の Web アプリを作る（30 分チュートリアル）
- 仮定・逸脱：定番の骨子からの逸脱はない。入力の「よくあるエラー」は独立した章にせず、該当ステップの「結果の確認」の直後に「うまくいかないとき」として 1〜2 行で置く（説明を詰め込んで手順の流れを止めないため）。見出しは「〜を作成する」のように動詞の形にそろえた。

## 骨子
1. はじめに（役割：作るもの・完成像・所要時間を示す／目安：5%）
   - 入れる要素：完成画面のスクリーンショット、所要時間 30 分、対象読者（HTML を触ったことがある人）
2. このチュートリアルで学ぶこと（役割：学習目標3項目／目安：3%）
   - 入れる要素：仮想環境を作れる、Flask アプリを起動できる、ルートを追加できる
3. 前提条件と準備（役割：必要な環境と確認方法／目安：7%）
   - 入れる要素：Python のインストール確認
4. ステップ1：仮想環境を作成する（役割：操作→結果の確認／目安：14%）
   - 入れる要素：作成と有効化のコマンド、プロンプトの変化で確認、うまくいかないとき（仮想環境の有効化忘れ）
5. ステップ2：Flask をインストールする（役割：操作→結果の確認／目安：10%）
   - 入れる要素：インストールコマンド、バージョン表示で確認
6. ステップ3：app.py を作成する（役割：操作→結果の確認／目安：16%）
   - 入れる要素：最小のコード全文、保存場所の確認
7. ステップ4：開発サーバーを起動してブラウザで確認する（役割：操作→結果の確認／目安：16%）
   - 入れる要素：起動コマンド、ブラウザに「こんにちは」が表示される画面、うまくいかないとき（ポート競合）
8. ステップ5：ルートを1つ追加する（役割：操作→結果の確認／目安：14%）
   - 入れる要素：追加するコード、再読み込みで確認
9. 動作確認（役割：2つのルートが動くことを通しで確認する／目安：5%）
   - 入れる要素：確認手順のチェックリスト
10. まとめ（役割：学んだことの振り返り／目安：5%）
    - 入れる要素：学習目標3項目の再掲
11. 次のステップ（役割：次に読む文書への案内／目安：5%）
    - 入れる要素：テンプレートとフォーム入力のチュートリアルへのリンク

## 構成チェック
- [x] 主要メッセージが冒頭3文以内にあるか（積み上げ型なら、完成像か目標が冒頭にあるか）
  - 判定理由：積み上げ型のため、完成像と所要時間を「はじめに」の第1文に置いた
- [x] 見出しだけで筋が通るか。標題と見出しが呼応しているか
  - 判定理由：標題の「最初の Web アプリを作る」に対し、ステップ1〜5 が作成手順の順に並ぶ
- [x] 各セクションの目的が1つか。同じ階層の見出しが MECE か
  - 判定理由：1ステップ1操作で、概念の説明は入れない
- [x] 読者の目的に不要な章がないか。範囲・前提・扱わないことを宣言しているか（長文の場合）
  - 判定理由：前提条件を独立節にし、「はじめに」で対象読者を宣言した
- [x] 意思決定文書に代替案・リスク・判断事項があるか。定型の必須セクションがそろっているか
  - 判定理由：意思決定文書ではないため前半は該当なし。カタログの定番骨子の節はすべて含む
- [x] 文体がジャンルの既定に合い、統一されているか
  - 判定理由：敬体で統一
```

## 例 (c) Zenn 向けの技術記事

### 入力（ハーネスから）

- 目的：理解する（開発者に経験・知見を共有する）。
- 読者：Web バックエンド開発者。専門性は中級。読む姿勢は拾い読み。
- メッセージ：「GitHub Actions の CI を 12 分から 4 分に短縮できた。効いたのは依存関係のキャッシュとテストの並列化で、Docker レイヤーキャッシュはほとんど効かなかった」。種別：提言（主張と経験）。
- 内容：時系列とデータ中心。要素：対象リポジトリの規模と構成（Node.js 20、pnpm、Jest）、改善前の計測値（ジョブ別の所要時間）、試した4施策（依存関係キャッシュ、テスト並列化、Docker レイヤーキャッシュ、ジョブ分割）とそれぞれの効果、設定ファイルの抜粋、ハマりどころ（キャッシュキーの設計）、参考リンク（GitHub Actions と Jest の公式ドキュメント）。
- 制約：Zenn（Web、Markdown）。分量の目安は 5,000 字。社外公開。指定書式なし。

### 出力

```markdown
## 構成選択結果
- 採用構成：技術記事（Qiita/Zenn 型）（型：結論ファースト。結論→背景→方法→結果→まとめ）
- 第2候補：ハウツー／手順書 — 採用しなかった理由：読者に手順を再現させることより、何が効いて何が効かなかったかという経験の共有が主目的のため。
- 選択理由：読者の目的は「理解する」のうち経験・知見の共有で、読者は開発者・拾い読み、メッセージは主張と経験なので、選択マトリクスの「知見を得る／開発者・拾い読み／主張と経験」に従い技術記事を選んだ。拾い読みする読者が冒頭で自分に関係あるかを判断できるよう、「はじめに」に結論・対象読者・前提環境とバージョンを置く。Web 媒体なので H2 を目次として機能させる。
- 核メッセージの位置：両方 — 「はじめに」の第1文と「まとめ」の第1文
- 文体：敬体 標題案：GitHub Actions の CI を 12 分から 4 分に短縮した話：効いた施策と効かなかった施策
- 仮定・逸脱：定番の骨子からの逸脱はない。入力の目的「理解する」は、メッセージが経験に基づく主張のため選択マトリクスの「知見を得る」行として扱った。設定ファイルの抜粋は「やったこと」の各施策の中に置き、手順書の区画は作らない（1区画に2つの型を混ぜない）。4施策は試した順ではなく効果の大きい順に並べる（時系列の日記にしないため）。Qiita/Zenn の慣習は実務上の慣行として扱う。

## 骨子
1. はじめに（役割：結論・対象読者・前提環境とバージョン／目安：10%）
   - 入れる要素：12 分→4 分、効いた施策2つと効かなかった施策、対象読者（GitHub Actions で Node.js の CI を回している人）、Node.js 20／pnpm／Jest の構成
2. 背景・課題（役割：改善前の状態と計測／目安：15%）
   - 入れる要素：リポジトリの規模、改善前のジョブ別所要時間
3. やったこと（役割：試した4施策を効果の大きい順に、設定抜粋と効果つきで示す／目安：40%）
   - 入れる要素：3.1 依存関係のキャッシュ、3.2 テストの並列化、3.3 ジョブの分割、3.4 Docker レイヤーキャッシュ（効かなかった理由）、各施策の設定ファイルの抜粋
4. 結果（役割：改善前後の比較表／目安：10%）
   - 入れる要素：施策ごとの効果、合計の 12 分→4 分
5. ハマりどころ・注意点（役割：再現する読者が詰まる点／目安：15%）
   - 入れる要素：キャッシュキーの設計
6. まとめ（役割：結論の再掲／目安：5%）
   - 入れる要素：12 分→4 分の再掲、効いた施策・効かなかった施策の一覧
7. 参考文献（役割：公式ドキュメントへのリンク／目安：5%）
   - 入れる要素：GitHub Actions の公式ドキュメント、Jest の公式ドキュメント

## 構成チェック
- [x] 主要メッセージが冒頭3文以内にあるか（積み上げ型なら、完成像か目標が冒頭にあるか）
  - 判定理由：「はじめに」の第1文に結論がある
- [x] 見出しだけで筋が通るか。標題と見出しが呼応しているか
  - 判定理由：標題の「短縮」「効いた施策と効かなかった施策」が「やったこと」「結果」「まとめ」に対応する
- [x] 各セクションの目的が1つか。同じ階層の見出しが MECE か
  - 判定理由：施策の説明と結果の比較を分けた
- [x] 読者の目的に不要な章がないか。範囲・前提・扱わないことを宣言しているか（長文の場合）
  - 判定理由：「はじめに」で対象読者と前提環境を宣言した
- [x] 意思決定文書に代替案・リスク・判断事項があるか。定型の必須セクションがそろっているか
  - 判定理由：意思決定文書ではないため前半は該当なし。カタログの定番骨子の節はすべて含む
- [x] 文体がジャンルの既定に合い、統一されているか
  - 判定理由：敬体で統一
```
