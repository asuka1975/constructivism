# 構成カタログ：技術ドキュメント系

出典：調査レポート 3.1「技術ドキュメント系」。各ジャンルを「適用条件／骨子／メッセージの位置／目安分量／アンチパターン／日本語の慣習」の6項目に統一して転記した。レポートに記載のない項目は「レポートに記載なし」と明記し、レポートの他章（第2章の決定木、第4章の文体の既定、5.3 のチェックリスト）から補える場合のみその旨を付して補った。レポートの根拠・備考は「適用条件」の補足として残した。

分量の目安はレポートの経験則で、一次情報で規定されている数値はその旨を明記している。文体の既定（第4章）：論文・リファレンス・仕様書・ADR は常体、それ以外は敬体。

## チュートリアル

- **適用条件**：初学者が手を動かして初めて成功するための文書。ハウツーとの違いは、読者がまだ「何がわからないかもわからない」こと（Diátaxis）。
- **骨子**：はじめに（作るもの・完成像・所要時間、5%）→ 学習目標（3項目程度）→ 前提条件と準備 → ステップ1〜n（各ステップに「操作→結果の確認」、70%）→ 動作確認 → まとめ（学んだこと）→ 次のステップ
- **メッセージの位置**：冒頭に完成像を示し、本論は積み上げる。
- **目安分量**：はじめに 5%、ステップ1〜n で 70%（レポートの経験則）。
- **アンチパターン**：説明を詰め込み、手順の流れを止める（Diátaxis が典型的な失敗として挙げている）。
- **日本語の慣習**：敬体。見出しは「〜を作成する」のように動作名詞か動詞の形にする。

## ハウツー／手順書

- **適用条件**：目標を持つ実務者が特定の課題を解く文書。
- **骨子**：概要（達成できること、1〜2文）→ 前提条件 → 手順（番号付き、1ステップ1操作）→ 結果の確認 → トラブルシューティング（任意）→ 関連情報
- **メッセージの位置**：冒頭（何ができるか）。
- **目安分量**：概要は1〜2文。それ以外はレポートに記載なし。
- **アンチパターン**：概念の説明や網羅的なオプション一覧を混ぜる（リファレンスと解説へ回す）。
- **日本語の慣習**：手順は「〜します」か「〜する」で統一し、1文に1操作とする。

## ランブック（一次情報未確認・一般的な実務慣行）

- **適用条件**：レポート 3.1 に記載なし。第2章の決定木では「作業する」のうち「障害対応・定常運用」に割り当てられている。
- **骨子**：対象アラートとサービス → 影響と緊急度の判断基準 → 初動手順 → 診断手順 → 復旧手順 → エスカレーション先 → 事後作業 → 更新履歴
- **メッセージの位置**：冒頭（このページを使う条件）。
- **目安分量**：レポートに記載なし。
- **アンチパターン**：背景説明が長く、初動手順が埋もれる。
- **日本語の慣習**：レポートに記載なし。文体の既定は敬体（第4章）。

## リファレンス／API ドキュメント

- **適用条件**：検索して事実を確かめる読者向け。Diátaxis によれば、リファレンスはユーザーのニーズではなく、記述対象である製品の構造に従って組み立てる。
- **骨子**（1項目あたり）：名前 → 概要（1文）→ 構文・シグネチャ → パラメーター（表）→ 戻り値 → エラー → 例 → 関連項目
- **メッセージの位置**：各項目の冒頭に1文の要約。
- **目安分量**：概要は1文。それ以外はレポートに記載なし。
- **アンチパターン**：教えようとする（使い方の物語を混ぜる）。
- **日本語の慣習**：常体か体言止めの表形式が読みやすい（文体の既定も常体、第4章）。

## 解説記事（explanation）

- **適用条件**：「なぜそうなっているか」を理解したい読者向け。
- **骨子**：導入（問い・この記事でわかること）→ 背景 → 中心概念 → 仕組み・理由 → 比較・トレードオフ → よくある誤解 → まとめ → 参考
- **メッセージの位置**：冒頭で答えの要旨を示し、本論で展開する。
- **目安分量**：レポートに記載なし。共通の目安として序論が全体の2割を超えない（5.3）。
- **アンチパターン**：手順を混ぜる、結論が出てこない。
- **日本語の慣習**：レポートに記載なし。文体の既定は敬体（第4章）。

## 技術記事（Qiita/Zenn 型）

- **適用条件**：開発者が経験や知見を共有する記事。拾い読みする読者に「自分に関係あるか」をすぐ判断させる。
  - 備考：Qiita/Zenn の慣習は一次情報を確認できておらず、プラットフォームの公式規定ではなく実務上の慣行として扱う。
- **骨子**：はじめに（結論・対象読者・前提環境とバージョン、10%）→ 背景・課題 → やったこと・方法 → 結果 → ハマりどころ・注意点 → まとめ → 参考文献
- **メッセージの位置**：冒頭（TL;DR かまとめを先に）。
- **目安分量**：はじめに 10%（レポートの経験則）。それ以外はレポートに記載なし。
- **アンチパターン**：経緯の日記になる、環境やバージョンを書かない。
- **日本語の慣習**：レポートに記載なし。文体の既定は敬体（第4章）。

## デザインドキュメント

- **適用条件**：解決策があいまいで、組織の合意が必要な技術判断。
  - 備考：RFC は統一された一次情報がなく、プロジェクトごとにテンプレートが異なるため、この骨子を基本形としてよい。
- **骨子**（Google 型）：メタ情報（作成者・状態・レビュアー）→ 背景とスコープ → 目標と非目標 → 概要（提案の要旨）→ 詳細設計（システム構成図・API・データ）→ 横断的関心事（セキュリティ・プライバシー・可観測性）→ 検討した代替案 → 未解決事項
  - 非目標とは、「システムがクラッシュしない」のような目標の否定ではなく、目標にもなり得たが、あえて目標にしないもの（レポート第1章 原理4）。
- **メッセージの位置**：「概要」で提案を先に示す。
- **目安分量**：レポートに記載なし。
- **アンチパターン**：非目標がない（スコープが際限なく広がる）、代替案が形だけ。
- **日本語の慣習**：レポートに記載なし。文体の既定は敬体（第4章）。

## ADR（Nygard 形式）

- **適用条件**：重要なアーキテクチャ上の決定を1件ずつ記録する。
- **骨子**：タイトル（決定内容を表す短い名詞句）→ ステータス（提案／承認／廃止／置換）→ コンテキスト（決定を迫る力学）→ 決定（「〜を採用する」と能動的に）→ 結果（良い・悪い・中立的な影響）
- **メッセージの位置**：タイトルと「決定」。
- **目安分量**：1〜2ページ。
- **アンチパターン**：複数の決定を1件にまとめる、置き換えられた ADR を削除する（Nygard は削除せず置換と記録することを勧めている）。
- **日本語の慣習**：レポートに記載なし。文体の既定は常体（第4章）。

## 要件定義書・仕様書

- **適用条件**：開発の前提となる合意事項を参照するとき。
  - 根拠：IPA『共通フレーム2013』（2013年3月）の要件定義プロセスが定める分類。ただし共通フレームは文書の種類や書式を規定しないため、下の目次は分類に基づく推奨形で、公式テンプレートではない。IPA『ユーザのための要件定義ガイド 第2版』（2019年）は、成果物を「要件定義ドキュメント群」として扱っている（第7章 DD.1 ビジネスコンセプト〜DD.13 運用・移行・総合テストの要求）。
- **骨子**：文書の目的と範囲 → 用語定義 → 業務要件（業務内容・手順・ルール・業務用語・外部環境）→ 組織と環境の要件 → 機能要件（機能間のデータの流れ・人とシステムの分担・外部インタフェース）→ 非機能要件（品質・技術・運用と操作・移行・付帯作業・その他）→ 前提・制約 → 未決事項
- **メッセージの位置**：レポートに記載なし。
- **目安分量**：レポートに記載なし。
- **アンチパターン**：要求（なぜ）と仕様（何を）が混在する、非機能要件が抜ける。
- **日本語の慣習**：レポートに記載なし。文体の既定は常体（第4章）。

## マニュアル

- **適用条件**：レポート 3.1 に記載なし。第2章の決定木では「作業する」のうち「製品全体の操作」に割り当てられている。
- **骨子**：はじめに（対象読者・本書の使い方・表記規則）→ 安全上の注意（該当時）→ 概要（全体像）→ 準備 → 基本操作（タスク別）→ 応用操作 → 困ったとき → 仕様・付録 → 索引
- **メッセージの位置**：レポートに記載なし。
- **目安分量**：レポートに記載なし。
- **アンチパターン**：画面や機能の順に並べる（読者がやりたいタスクの順に並べる）。
- **日本語の慣習**：JTCA『日本語スタイルガイド』の表記規則に従うと一貫性を保ちやすい。文体の既定は敬体（第4章）。

## FAQ

- **適用条件**：レポート 3.1 に記載なし。第2章の決定木では「調べる」のうち「よくある疑問」に割り当てられている。
- **骨子**：カテゴリ別の Q&A（問いは読者の言葉で書き、答えの1文目で結論を言う）→ 解決しない場合の問い合わせ先
- **メッセージの位置**：各答えの1文目（骨子の記述から）。
- **目安分量**：レポートに記載なし。
- **アンチパターン**：実際には誰も聞かない質問、本来はハウツーにすべき長い手順の詰め込み。
- **日本語の慣習**：レポートに記載なし。文体の既定は敬体（第4章）。

## リリースノート

- **適用条件**：レポート 3.1 に記載なし。第2章の決定木では「報告を受ける」のうち「変更」に割り当てられている。
- **骨子**：バージョンと日付 → ハイライト（1〜3行）→ 破壊的変更と必要な対応（最上位）→ 新機能 → 改善 → バグ修正 → 既知の問題 → 非推奨と削除予定
- **メッセージの位置**：読者が対応を必要とする変更を先頭に置く。
- **目安分量**：ハイライトは1〜3行。それ以外はレポートに記載なし。
- **アンチパターン**：レポートに記載なし。
- **日本語の慣習**：レポートに記載なし。文体の既定は敬体（第4章）。
