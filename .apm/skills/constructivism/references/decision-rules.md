# 構成選択ルール（判断軸・決定木・選択マトリクス）

出典：調査レポート第2章「構成選択ルール」をそのまま転記したもの。SKILL.md の判断手順2（系統の決定）で読み込む。

## 1. 判断軸の定義（支配度の高い順）

| 順位 | 判断軸 | 取り得る値 | 構成への効き方 |
|---|---|---|---|
| 0 | 定型の有無 | 組織・業界・法令の書式あり／なし | ありならそれを骨格として採用し、以下の軸は中身の調整にだけ使う |
| 1 | 読者の目的 | 決める（承認）／報告を受ける／作業する／学ぶ／調べる／理解する／動かされる（依頼・説得）／検証する（学術） | 構成の系統（ジャンル）を決める |
| 2 | 読む姿勢・時間 | 通読／拾い読み・検索／冒頭だけ（多忙な意思決定者） | 結論の位置、要約の要否、見出しの粒度を決める |
| 3 | メッセージ種別 | 主張・提言／意思決定の記録／事実の報告／手順の指示／概念の説明／比較評価／教育 | 同じ系統の中での型を決める（PREP か SDS か、ADR かデザインドキュメントか） |
| 4 | 内容種別 | 手順的／概念的／参照的／物語的（時系列）／データ中心 | 本論の展開パターンを決める（時系列、問題→解決、原因→結果、比較対照、分類、一般→具体） |
| 5 | 専門性 | 初学者／中級／専門家 | 前提説明・用語定義・例の量と、詳細へ進む速さを決める |
| 6 | 寿命・形式性・媒体・分量 | 一時連絡か長期参照か／社内か社外か、上位者宛か、公的か／メール、Wiki、PDF、Web／上限字数 | 文体（敬体か常体か）、メタ情報欄、要約や目次の有無、圧縮の度合いを決める |

## 2. 決定木

```
Q0 組織・法令・媒体の指定書式があるか？
  はい → 指定書式を骨格に採用。Q2以降で中身を調整
Q1 読者は読後に何をするか？
  承認・決定する
    金額・権限の決裁 → 稟議書／決裁文書
    新規施策の採否 → 企画書・提案書（PREP/SCQA）→ 長文なら Amazon型ナラティブ／PR/FAQ
    技術方式の合意 → デザインドキュメント／RFC
    決定済み事項の記録 → ADR
  報告を受ける
    進捗・調査結果 → 報告書（SDS）／障害 → ポストモーテム
    会議 → 議事録（決定事項先頭）／変更 → リリースノート
  作業する
    1つの目標達成 → ハウツー／手順書／障害対応・定常運用 → ランブック
    製品全体の操作 → マニュアル（タスク別章立て）
  学ぶ → 手を動かして習得：チュートリアル／体系的知識：教材の章
  調べる → 仕様・API：リファレンス／要件：要件定義書／よくある疑問：FAQ
  理解する → 概念・理由：解説記事／経験・知見：技術記事（Qiita/Zenn 型）
  動かされる → 周知：社内通知／依頼・説得：依頼メール（PREP）・訴求文（AIDA）
  検証する → 学術論文（IMRaD、Abstract で結論先出し）
  要点だけ知る → エグゼクティブサマリー／1枚もの（BLUF）
Q2 結論の位置
  既定：冒頭（結論ファースト／BLUF／PREP／SDS）
  状況が共有されていない・反対が予想される → SCQA（答えは冒頭1段落以内）
  学習順序に意味がある → 冒頭は完成像と学習目標、本論は積み上げ
  論文 → Abstract に結論、本文は IMRaD の順
Q3 専門性
  初学者 → 前提・用語定義・概念→例の順。前提条件セクションを独立
  専門家 → 結論・差分・詳細へ直行。背景は1段落か付録へ
Q4 媒体・分量
  メール・チャット → 件名で要件、冒頭で結論と依頼事項
  Web・Wiki → H2 を目次として機能させる
  上限字数あり → 第2階層以下を削り、第1階層の骨子は保つ
```

## 3. 選択マトリクス（入力 → 推奨構成）

| 読者の目的 | 読者・姿勢 | メッセージ種別 | 第1候補 | 第2候補 | 選択理由 |
|---|---|---|---|---|---|
| 承認する | 経営層・冒頭だけ | 提言 | エグゼクティブサマリー＋稟議書 | 企画書（PREP） | 決裁者は金額・効果・リスクを所定の位置で探す |
| 承認する | 管理職・通読 | 提言 | 企画書・提案書（SCQA→提案→根拠） | Amazon 型ナラティブ | 状況の共有が必要な新規施策 |
| 合意する | エンジニア・通読 | 比較評価 | デザインドキュメント | RFC | 目標・非目標・代替案の明示が合意の前提 |
| 記録を残す | 将来のメンバー・検索 | 意思決定の記録 | ADR | デザインドキュメントの代替案節 | 1決定1記録で時点の文脈を保存 |
| 報告を受ける | 上司・拾い読み | 事実の報告 | 報告書（SDS） | エグゼクティブサマリー | 要点→詳細→要点で全体像を渡す |
| 報告を受ける | 関係者・通読 | 事実と再発防止 | ポストモーテム | 障害報告書（社外向け） | 影響・原因・対策を定位置に置く |
| 作業する | 実務者・拾い読み | 手順の指示 | ハウツー／手順書 | ランブック | 目標達成への最短経路 |
| 学ぶ | 初学者・通読 | 教育 | チュートリアル | 教材の章 | 成功体験を優先し説明は最小限 |
| 学ぶ | 学生・通読 | 教育 | 教材の章（目標→概念→例→演習→まとめ） | 解説記事 | 教授事象の順序に沿う |
| 調べる | 実務者・検索 | 事実 | リファレンス | FAQ | 製品の構造に沿った一貫した並び |
| 理解する | 中級者・通読 | 概念の説明 | 解説記事 | 技術記事 | 「なぜ」に答える |
| 知見を得る | 開発者・拾い読み | 主張と経験 | 技術記事（結論→背景→方法→結果→まとめ） | ハウツー | 冒頭で関係の有無を判断させる |
| 動かされる | 社員全体・冒頭だけ | 周知 | 社内通知（標題で性格を示し要点→詳細） | FAQ 付き通知 | 行動と期限を最初に示す |
| 動かされる | 社外・通読 | 依頼 | 依頼メール（PREP） | 提案書 | 依頼事項と期限を冒頭に |
| 検証する | 研究者・モジュール読み | 主張と証拠 | IMRaD 論文 | 短報 | 定位置で情報を拾える |
